# Payment System Plan — Freemium Subscriptions

**Status: Phases 0-2 shipped and live-verified 2026-08-13/14.** Real bugs found via actual testing (not just code review), all fixed:
- **ESM import-ordering bug**: module-level `process.env.X` reads in `server/billing.ts`/`rateLimiter.ts`/`stripe.ts` executed before `server.ts`'s own `dotenv.config()` (ES imports are hoisted ahead of the importing file's body) — silently fine in Phase 0 since defaults happened to match, broke Phase 1 outright (Stripe Price IDs always read as empty). Fixed by converting all of them to lazy functions.
- **Missing `customer.subscription.created` webhook handler** — Stripe fires `created`, not `updated`, on a brand-new subscription; only `.updated` was wired up, so `subscriptionCurrentPeriodEnd` silently never got set on first subscribe. Fixed by having `FirestoreDataStore.getBilling()` fall back to a default free-plan object instead of `null`; `null` is now reserved for true local-only mode.

Verified end-to-end with a real Stripe test-mode purchase (webhook → Firestore → UI all correct) and against two real accounts — one Pro Monthly, one freshly-created free account — confirming the paywall, quota display, and Customer Portal all behave correctly for each.

## Pricing tiers (as specified 2026-08-13)

| Tier | Billing | AI actions | AI cost borne by | Job Analysis (Matches) |
|---|---|---|---|---|
| **Free** | — | 20 total, lifetime (never resets) | App (platform Gemini key) | ❌ locked |
| **Pro Monthly** | Monthly | 100/month, resets on billing cycle | App (platform Gemini key) | ✅ unlocked |
| **BYOM Monthly** | Monthly | No app-side cap (abuse-guard ceiling — see below) | User's own provider key | ✅ unlocked |
| **BYOM Yearly** | Yearly | No app-side cap (abuse-guard ceiling — see below) | User's own provider key | ✅ unlocked |

**Abuse-guard ceiling recommendation** (for BYOM tiers — this isn't a monetization limit, it's a circuit-breaker so a bug on this app's side, like an infinite-retry loop or a runaway `useEffect`, can't silently hammer a user's own paid API key without their knowledge): use **two layers**, not one flat number —
- **Burst cap: 30 calls/minute per user.** A fast runaway loop can fire hundreds of calls a minute if nothing stops it; a per-minute cap catches that within seconds instead of a whole day. 30/minute is comfortably above realistic human-paced usage — even bulk-pasting a big batch of jobs into Matches (each posting = one `liteScan` call) is very unlikely to clear 30 requests inside 60 seconds — while still being far below what an unthrottled bug could do.
- **Daily ceiling: 500 calls/day per user.** Backstop for a slower-burning bug that stays under the per-minute cap but keeps firing for hours. 500 is well above even a heavy real session (large Matches triage batch + several full job-pipeline runs + a long journey-building chat in one day), so a legitimate BYOM user should never actually see it.
- Both numbers live in Phase 5's `config/featureFlags` doc, so they're adjustable without a redeploy — start here, then watch Phase 7's real usage data and loosen/tighten if either ceiling turns out wrong in practice.
- Log (don't just silently 429) whenever either ceiling is hit — a BYOM user hitting it is itself a signal worth Blair seeing, since it means either a genuine bug or unusually heavy legitimate use that should inform the next tuning pass.

Exact prices ($ amounts) are Blair's call in the Stripe Dashboard, not a code decision — the app treats them as configured Price IDs, not hardcoded numbers.

## Where the app is today (grounds this plan)

- **Auth**: Firebase Auth, self-service email/password sign-up + a shared demo account (`src/components/AuthGate.tsx`). No account roles or custom claims exist at all.
- **Data**: Firestore, every doc under `users/{uid}/...`, rules key off `request.auth.uid` only (`firestore.rules`). No per-user profile/plan doc exists yet.
- **AI usage control**: `server/rateLimiter.ts` — one flat in-memory daily call cap (`AI_DAILY_CALL_LIMIT`, default 50) applied uniformly to every signed-in user. No concept of free vs. paid, no persistence (resets on server restart).
- **AI calls today are Gemini-only and hardcoded**: `server.ts` builds one module-level `GoogleGenAI` client from `process.env.GEMINI_API_KEY` and every one of the ~18 `/api/ai/*` endpoints calls it directly, with the structured-output schema written ad hoc per endpoint using Gemini's `Type.OBJECT`/`Type.STRING` format. There is no schema-once/provider-agnostic layer today — BYOM-with-provider-choice requires building one (see Phase 3).
- **"Admin"**: `src/pages/AdminPrompts.tsx` / `/api/admin/*` in `server.ts` exist (prompt-config editing) but are gated only by `requireFirebaseAuth` — **any signed-up user can currently hit them**, not just an operator. There is no admin-role concept to fix this with yet.
- **Server**: single Express app (`server.ts`), `express.json()` mounted globally before all routes — relevant because Stripe webhook signature verification needs the *raw* request body, so the webhook route must be registered before that global JSON parser (or use a route-scoped raw parser).
- **No billing, no legal pages (Terms/Privacy/Refund), no transactional email sending beyond Firebase Auth's built-in verification email.**

## Brainstorm — everything a real freemium payment system needs

1. **Billing provider integration (Stripe)**: one Product, three Prices (Pro Monthly, BYOM Monthly, BYOM Yearly), Checkout Sessions (hosted — card data never touches this server), Customer Portal for self-service plan management/cancellation, webhooks as the async source of truth.
2. **Entitlement data model**: a per-user plan/subscription record in Firestore mirroring Stripe state via webhooks (never trust client-reported plan status).
3. **Feature gating, two shapes**: a **hard gate** (Matches simply refuses to run below any paid plan) and a **soft gate/usage quota** (Free's 20-lifetime-action allowance, Pro Monthly's 100/month).
4. **Multi-provider AI routing (new, driven by BYOM-with-choice)**: an abstraction so the same 18 endpoints can run against the platform's Gemini key *or* a user-supplied Gemini/OpenAI/Anthropic key, without duplicating every prompt+schema per provider.
5. **Key handling, never persisted**: BYOM users hand the app live credentials to their own paid AI accounts. **Decision (2026-08-13): the key is never stored server-side at all** — client-side only (localStorage), sent per-request alongside the existing Firebase bearer token, held in server memory only for the duration of that one call, never logged, never in error telemetry, never written to Firestore. This trades minor multi-device friction (re-enter per browser) for eliminating the much larger liability of centrally holding a pool of other companies' live API credentials — a single incident on this app's side would otherwise expose every BYOM user's provider account at once.
6. **Admin roles & feature flags**: a real `isAdmin` concept (Firebase custom claims) to fix the currently-open `/api/admin/*` routes and run an admin console for comping accounts, kill-switches, and adjusting the free/Pro limits without a redeploy.
7. **Legal/compliance**: Terms of Service, Privacy Policy, Refund Policy — required before charging real money; sales tax/VAT handling (Stripe Tax). BYOM adds a wrinkle worth a line in the ToS: the user is responsible for their own provider's costs/usage terms, the app is just a pass-through.
8. **Transactional email**: Stripe's built-in receipts/dunning need zero code; anything custom needs an email provider this app doesn't have yet.
9. **Downgrade/cancellation correctness**: on lapse, degrade to Free gates cleanly, never delete data; a BYOM user who cancels should have their stored key handling decided explicitly (keep it for if they resubscribe vs. purge it — recommend purge on cancellation, re-enter on resubscribe, simplest and safest).
10. **Webhook reliability**: signature verification, idempotency (Stripe can redeliver the same event).
11. **Demo account**: the shared demo login is a sales surface — should always show the full Pro experience via a pre-comp, not hit the same paywall a real free user would.
12. **Cost guardrails**: for platform-key tiers (Free, Pro Monthly), track estimated Gemini cost per user against revenue; for BYOM tiers there's no app-side AI cost, but a runaway-loop abuse-guard cap still matters so a bug can't silently hammer a user's own paid key.
13. **Testing**: Stripe test mode + Stripe CLI (`stripe listen`) for local webhook testing; per-provider key validation testing (a real OpenAI/Anthropic/Gemini test key exercised end to end) before launch.

## Phase plan

### Phase 0 — Entitlement foundation (no Stripe yet)
- New Firestore doc holding per-user billing state (fits alongside the existing per-user data in `FirestoreDataStore.ts`): `plan: 'free' | 'pro_monthly' | 'byom_monthly' | 'byom_yearly'`, `stripeCustomerId`, `subscriptionStatus`, `subscriptionCurrentPeriodEnd`.
- Separate AI-usage doc: `freeAiActionsUsed` (counts up, **never resets** — Free's cap is lifetime), `proMonthlyAiActionsUsed` + `proMonthlyPeriodStart` (resets each billing cycle for Pro Monthly only).
- Firestore rules: these billing/usage fields must be **server-write-only** (Admin SDK) — a client-side write path would let a user grant themselves Pro from devtools. Everything else in `users/{uid}/...` keeps today's owner-read/write rule.
- Real admin concept: one-off script to set a Firebase custom claim (`admin: true`) on Blair's account; `requireAdmin` middleware in `server/firebaseAdmin.ts`; apply to `/api/admin/*`, closing the currently-open gap.
- Replace the flat rate limiter with a plan-aware one reading the new usage doc: Free → hard stop at 20 lifetime actions; Pro Monthly → hard stop at 100 for the current period; BYOM tiers → the two-layer abuse-guard ceiling above (30/minute burst + 500/day), both read from `config/featureFlags` (Phase 5) so they're tunable without a redeploy.

**Harden the platform Gemini key** (this key keeps powering Free and Pro Monthly under this plan — BYOM tiers are the only ones that stop using it — so real subscription revenue starts depending on it staying available, not just secret):
- **Confirm Secret Manager, not a plain env var, in Cloud Run.** If `GEMINI_API_KEY` is currently injected via a literal `--set-env-vars` value, migrate it (and, once they exist, `STRIPE_SECRET_KEY` and `FIREBASE_SERVICE_ACCOUNT_JSON`) to Google Secret Manager references instead — adds IAM-scoped access control, versioning, and an access audit log, instead of a value visible to anyone with read access to the Cloud Run service config.
- **Add a GCP billing budget alert** on the project so an unusual spend spike (leaked key, abuse, or a runaway-call bug) surfaces as a notification instead of a surprise invoice — pairs with the plan-aware quota above as a second, independent line of defense.
- **Make the auth gate fail closed in production, not open.** Today `requireFirebaseAuth` (`server/firebaseAdmin.ts`) silently passes every request through unauthenticated whenever `FIREBASE_SERVICE_ACCOUNT_JSON` isn't set — correct behavior for local dev, but dangerous if that variable is ever missing or empty in the real deployment by mistake, since every AI endpoint would silently open to anyone with the URL with no error raised. Add an explicit deploy-mode signal (e.g. a `REQUIRE_FIREBASE_AUTH=true` flag set only in the real Cloud Run config, or checking `NODE_ENV === 'production'`) so that in that mode, a missing service-account config makes the server refuse to start (or hard-403 every gated route) instead of silently falling through — local dev keeps today's no-op convenience untouched.
- Verification: confirm a non-admin account gets 403 on `/api/admin/*`; confirm Free's counter persists across a server restart and never resets; confirm Pro Monthly's counter resets when a new billing period starts; confirm the Cloud Run service's env config shows Secret Manager references rather than literal values; confirm a budget alert exists on the project; confirm that deliberately unsetting `FIREBASE_SERVICE_ACCOUNT_JSON` in a production-mode run refuses to start / hard-403s rather than passing requests through.

### Phase 1 — Stripe core integration (step-by-step, since Blair already has a Stripe account)
Manual Dashboard steps first, then the code that consumes them:

2. **Developers → API keys**: copy the test **Secret key** → `STRIPE_SECRET_KEY` in `.env`. Copy the test **Publishable key** too, in case Checkout needs it client-side (redirect-based Checkout usually doesn't, but keep it handy) → `VITE_STRIPE_PUBLISHABLE_KEY`.
3. **Product catalog → Add product**: create one product, e.g. "Career Journey Pro". Under it, add three **recurring Prices**:
   - `Pro Monthly` — monthly, platform-key tier.
   - `BYOM Monthly` — monthly, bring-your-own-key tier.
   - `BYOM Yearly` — yearly, bring-your-own-key tier.
   Copy each Price ID (`price_...`) into env vars: `STRIPE_PRICE_PRO_MONTHLY`, `STRIPE_PRICE_BYOM_MONTHLY`, `STRIPE_PRICE_BYOM_YEARLY`.
4. **Settings → Billing → Customer portal**: turn it on, allow plan switching between the three paid Prices and self-service cancellation. This is what powers Phase 2's "Manage billing" link — no custom UI needed for upgrade/downgrade/cancel.
5. **Local webhook testing**: install the Stripe CLI, `stripe login`, then `stripe listen --forward-to localhost:47293/api/billing/webhook`. It prints a `whsec_...` signing secret — put that in local `.env` as `STRIPE_WEBHOOK_SECRET`. Leave `stripe listen` running while testing locally; it forwards real test-mode events to your dev server.
6. **Production webhook** (once deployed): **Developers → Webhooks → Add endpoint**, URL = the deployed `/api/billing/webhook`, subscribe to `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`. This endpoint gets its **own** signing secret, separate from the CLI one — set it as `STRIPE_WEBHOOK_SECRET` in the production environment only.
7. Test purchases use Stripe's test card `4242 4242 4242 4242`, any future expiry, any CVC.

Code:
- Server endpoints: `POST /api/billing/createCheckoutSession` (body: which of the 3 Price IDs, authenticated, returns a redirect URL), `POST /api/billing/createPortalSession` (authenticated), `POST /api/billing/webhook`.
- The webhook route **must** be registered with a raw-body parser before `app.use(express.json())` in `server.ts`, or signature verification breaks.
- Webhook logic: `checkout.session.completed` → read which Price was purchased from the session, set `plan` accordingly + store `stripeCustomerId`; `customer.subscription.updated` → sync `subscriptionStatus`/`subscriptionCurrentPeriodEnd`, and if the Price changed (Portal plan switch) update `plan` to match; `customer.subscription.deleted` → revert to `plan: 'free'`; `invoice.payment_failed` → mark `past_due` (Stripe's own retry/dunning still runs).
- Idempotency: record processed Stripe event IDs in Firestore so a redelivered webhook doesn't double-apply.
- Verification: full test-mode purchase of each of the 3 Prices, confirm the billing doc updates correctly for each; use `stripe trigger customer.subscription.deleted` etc. for events that are awkward to reach by clicking through Checkout.

### Phase 3 — Multi-provider AI abstraction (new, required for BYOM-with-provider-choice)
This is the load-bearing piece of the BYOM tiers and the largest net-new engineering surface in this plan. Build the seam, prove it on a couple of endpoints, before touching the rest.
- Define a small provider interface, e.g. `generateStructured({ systemPrompt, prompt, schema, apiKey }) => Promise<T>`, with implementations:
  - `GeminiClient` — wraps the existing `@google/genai` usage.
  - `OpenAIClient` — new `openai` package dependency, structured output via JSON-schema response format.
  - `AnthropicClient` — new `@anthropic-ai/sdk` package dependency, structured output via tool-use with an input schema.
- Each endpoint's response shape needs a single provider-agnostic schema definition (zod is already a project dependency — reuse it) that each client implementation translates into its own provider's structured-output format, instead of the current per-endpoint hand-written Gemini `Type.OBJECT` schema.
- **Migrate 2–3 pilot endpoints first** (pick one simple like `keywords` and one complex/nested like `fitScore` or `auditGates`) to prove the pattern end-to-end against all three providers before migrating the remaining ~15. Worth flagging: this codebase has hit real bugs before from schema shape mismatches with structured-output APIs (Gemini returning `{}` for underspecified nested schemas, per prior work on this project) — verify each provider's structured output live, not just type-check, especially on nested/complex schemas.
- A factory `getAIClient({ uid, plan, byomHeader })` that resolves the platform Gemini client (Free/Pro Monthly) or a client built from the per-request BYOM key/provider/model carried in a request header (BYOM tiers, once Phase 4 lands) — Phase 3 can ship with the factory always returning the platform Gemini client; Phase 4 wires in real BYOM routing. No server-side key lookup/decryption step exists in this design — see Phase 4.
- Verification: same request run through Gemini, OpenAI, and Anthropic backends (manually, with real test keys for each) returns correctly-shaped, schema-valid output on both pilot endpoints.

### Phase 4 — BYOM settings, client-side key handling, and full endpoint migration
- Settings UI: a "Bring Your Own Model" panel (only relevant/shown for BYOM Monthly/Yearly accounts) — pick provider (Gemini/OpenAI/Anthropic), paste an API key, pick a model from that provider's allowed list (not a free-text model field, to avoid users pointing at unsupported/incompatible models).
- **The API key itself is never sent to Firestore or any server-side store.** It's saved in the browser's `localStorage`, scoped to that device/browser. Every AI request from a BYOM account attaches it via a custom header (e.g. `X-BYOM-Key`, `X-BYOM-Provider`, `X-BYOM-Model`) alongside the existing `Authorization: Bearer <firebase-id-token>` header. The server reads it into memory for that single request, uses it to call the chosen provider, and lets it go out of scope when the response is sent — never logged, never included in error reports, never written anywhere durable.
- Provider + model **choice** (not the key) is still stored server-side in a small per-user doc, since it's not a secret and the admin console (Phase 5) and rate limiter both want to know which provider a BYOM user is on. The key is the only thing excluded from persistence.
- New Firestore doc `config/allowedModels` (admin-write-only, same layering as Phase 5's feature flags), shape: `{ gemini: [{id, label, enabled}], openai: [...], anthropic: [...] }`. The BYOM picker only ever offers `enabled: true` entries. Seed it at launch with (see Open Decisions resolved below): Gemini — `gemini-2.5-pro` (flagship), `gemini-3.7-flash` (balanced/default), `gemini-3.5-flash-lite` (cost-efficient); OpenAI — `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`; Anthropic — `claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5-20251001`. Verify these IDs against each provider's docs at implementation time, since the model landscape moves fast and this list was compiled well before Phase 4 ships — the admin Models tab (Phase 5) is exactly for keeping it current afterward.
- **Key validation on entry**: a cheap real call to the chosen provider (e.g., a minimal completion or a models-list call), made through a server endpoint that takes the key in the request body, tests it, and returns valid/invalid **without storing it** — client only saves to localStorage after a successful validation. Never silently accept an untested key.
- Masking for display (`sk-...ab12`) happens entirely client-side, since the client already holds the raw value — no round-trip to the server needed.
- Wire Phase 3's `getAIClient({ uid, plan, byomHeader })` factory to build a provider client from the per-request header for BYOM-tier users; platform-key users unaffected.
- Migrate the remaining ~15 `/api/ai/*` endpoints onto the Phase 3 abstraction now that the pattern is proven.
- Error handling: distinguish "your key is invalid/missing/exhausted/rate-limited" (surfaced to the BYOM user, actionable — including "you're on a BYOM plan but haven't added a key yet, add one in Settings") from "something broke on our end" (generic error) — a BYOM user's own provider outage or a missing-key request shouldn't look like an app bug.
- Cancellation/logout: nothing to purge server-side by design; have the client clear the stored key from localStorage on downgrade from a BYOM tier or on sign-out, as tidy-up rather than a security necessity.
- Verification: a real BYOM account exercised end-to-end against a real key for each of the 3 providers across several endpoints, including a deliberately-invalid key and a request with no key header at all, to confirm both error paths; confirm via browser devtools that no request/response anywhere in the flow persists the raw key server-side.

## Resolved this session (2026-08-13, follow-up)

- **Abuse-guard ceiling**: two-layer default recommended and adopted — 30 calls/minute burst cap + 500 calls/day, both stored in Phase 5's `config/featureFlags` doc for later tuning. See the pricing-tiers section above for the full reasoning.
- **Model selection for BYOM**: not a fixed in-code list — admin-managed via a new `config/allowedModels` Firestore doc, with a dedicated "Models" tab in the Phase 5 admin console to add/enable/disable models per provider without a redeploy. Phase 4 reads from this doc from day one rather than hardcoding an array, so Phase 5 doesn't require re-plumbing anything. Initial seed list (verified against live provider docs 2026-08-13, re-check at implementation time): Gemini — `gemini-2.5-pro`, `gemini-3.7-flash`, `gemini-3.5-flash-lite`; OpenAI — `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`; Anthropic — `claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5-20251001`.
- **BYOM API key storage: never stored server-side.** Client-side only (`localStorage`), sent per-request via a custom header alongside the existing Firebase bearer token, held in server memory only for the duration of a single call, never logged/persisted/included in telemetry. Only the non-secret provider+model *choice* lives in Firestore. Chosen specifically to keep this app from becoming a centralized store of other companies' live API credentials — the liability of a breach exposing every BYOM user's key at once outweighs the minor multi-device re-entry friction.
